TypeTheory Engine

A proof engine for the Calculus of Inductive Constructions, the type theory of Lean and Rocq, written in pure Wolfram Language. Its terms are written with the symbols the language already has: Function, Typed, TypeOf, ForAll, Implies, Exists, Equal, Plus, NonNegativeIntegers. A small kernel checks every proof, and tactics build proofs step by step in a notebook.

Summary

  • An independent engineThe paclet WolframInstitute/TypeTheory needs nothing but the Wolfram Language. No symbol in it is named after Lean, and it loads and checks proofs without Lean installed. A bridge in LeanLink translates declarations in both directions, so the two kernels can check each other's work.
  • Two layers of termsCore terms are locally nameless, with internal heads named in plain words: boundVariable, lambdaAbstraction, dependentFunctionType, … Alpha-equivalence is SameQ. Surface terms are ordinary expressions built from built-in symbols, held inside TypeTheoryTerm, for reading and writing.
  • Built-in symbols are the constantsThe prelude declares Equal as the inductive equality type, NonNegativeIntegers as the natural numbers, and Plus as addition. n + 0 == n is therefore literally a statement of the theory.
  • TypeOf is the front doorTypeOf[TypeTheoryTerm[2 + 3]] gives TypeTheoryTerm[NonNegativeIntegers, prelude], shown as ℕ. The engine extends the built-in through an upvalue on TypeTheoryTerm, without modifying it.
  • A small trusted kernelType inference, reduction and definitional equality; inductive families with generated recursors; natural number literals. Elaboration and tactics sit outside it: whatever they produce is checked again with no holes left.
  • Explicit environmentsThere is no global environment. Declarations are inert constructors, such as TypeTheoryTheorem[name, statement, proof], that TypeTheoryEnvironment[env, {declaration, …}] or Append[env, declaration] checks into a new environment, leaving the old one as it was. An environment is a handle to a store, a symbol whose DownValues hold the constants, so terms and proofs carry theirs: TypeTheoryTerm[term, env], TypeTheoryProof[statement, env]. Where none is given, the environment is the prelude. A store can be changed by hand, so TypeTheoryCheck[env] replays every declaration from scratch.

Goals and non-goals

Goals

  1. Implement the Calculus of Inductive Constructions, as Lean 4's kernel defines it, in pure Wolfram Language, behind a small trusted kernel.
  2. Write statements and proofs with the language's own symbols, and read them back in mathematical notation.
  3. Build proofs interactively in a notebook, with the goals in view.
  4. Exchange declarations with Lean through a separate bridge, reaching the same verdicts as Lean's kernel.
  5. Use symbolic computation to find proofs, never to stand in for them.

Non-goals

  • Replacing Lean's elaborator, its tactic language or Mathlib.
  • Checking all of Mathlib in the Wolfram Language. Its 766,243 declarations stay with Lean's kernel, which LeanLink's "KernelCheck" already reaches.
  • A different type theory. The theory is Lean 4's, so that a proof checked here is a proof there.
  • Depending on Lean at run time.

The acceptance test is the classic pair. n + 0 == n holds by computation, because addition recurses on its second argument. 0 + n == n needs induction. Both are proved with tactics and declared, and each of the following is rejected:

  • a wrong proof;
  • an inductive type that occurs negatively in its own constructor;
  • a constructor field in a larger universe than its type;
  • large elimination from Or;
  • Type : Type;
  • an environment with a tampered record.

Representation

Core terms

The kernel works on internal heads, one per term former. They are package-scoped: users never write them, and they carry no Lean names. Each corresponds to one constructor of Lean 4's Expr, which is what makes a faithful bridge possible.

Core headMeaningLean Expr
boundVariable[i]A de Bruijn index, 0 for the innermost binder. Alpha-equivalent terms are identical expressions, so SameQ, Association keys and caches compare them structurally.bvar
freeVariable[id]A variable of a local context, which holds its name and type. Going under a binder opens it with a fresh one, so the kernel never handles loose indices.fvar
metavariable[id]A hole: an implicit argument while elaborating, or an open goal in a proof.mvar
universeSort[level]A universe. universeSort[0] is Prop.sort
constantReference[HoldComplete[name], {level, …}]A declared constant at universe levels. The name is held, so a symbol with a value never evaluates inside a term.const
application[f, a]Application, binary.app
lambdaAbstraction[HoldComplete[x], A, b, binder]A function. binder is "Explicit", "Implicit", "StrictImplicit" or "InstanceImplicit".lam
dependentFunctionType[HoldComplete[x], A, B, binder]A dependent function type, which covers ∀ and →.forallE
localDefinition[HoldComplete[x], A, v, b]A local definition.letE
projection[HoldComplete[S], i, t]Field i of t, counted from 0, where the type of t is the structure S.proj
naturalLiteral[n]A natural number of any size, a Wolfram integer.lit

Levels are integers, levelParameter, levelMetavariable, levelSuccessor[l, k], levelMaximum and levelImpredicativeMaximum. The last is 0 when its second argument is 0, which makes Prop impredicative. A normal form makes equal levels identical expressions. The order test is sound but incomplete: it may refuse a true inequality between levels with parameters, never accept a false one. String literals have no core head yet.

A surface term is the expression a person types, held. Wherever a built-in symbol has the right meaning, the engine uses it.

Keeping surface terms inert

The Wolfram Language evaluates whatever it is given. On the current version, ForAll[Typed[x, A], x >= 0] evaluates to x >= 0, because a quantifier whose variable does not occur is dropped. Element[2, Integers] evaluates to True, and n + 0 == n to True. So surface terms are always held:

  • TypeTheoryTerm has the HoldFirst attribute: the term is held, and the environment beside it is evaluated.
  • The declaration constructors TypeTheoryAxiom, TypeTheoryDefinition, TypeTheoryTheorem, TypeTheoryInductiveType and TypeTheoryNaturalNumbers are inert and hold their arguments, as do TypeTheoryProof and the tactics.
  • Internally a term becomes a syntax tree of inert nodes before anything inspects it. Names are kept as HoldComplete[name].

Bound variables are plain symbols: a binder scopes its variable, so no value reaches it, and Formal symbols would add nothing. A symbol whose value is a TypeTheoryTerm stands for that term, and one whose value is a finished proof stands for the proof, so statements and proofs can be built up across cells.

Moving between the layers

  • Surface to core is elaboration. It inserts implicit arguments and universe levels and solves them by unification; see Elaboration.
  • Core to surface is reading back. Binders get their own names back, or a numbered variant, as a1, where a variable in scope already shows the name; implicit arguments are dropped; and a non-dependent function type becomes Implies or TypeSpecifier. In a notebook the result shows in mathematical notation through an InterpretationBox, so copying a displayed term pastes the term itself. The connectives show as ∧, ∨ and ¬, and the natural numbers of the term's environment as 0 and n + 1, as Lean shows them.

The kernel

The kernel is the part that decides what counts as a theorem. It implements Lean 4's theory: dependent types, non-cumulative universes with Prop impredicative, inductive families, proof irrelevance, and eta for functions. Kernel functions report a failure by throwing a tagged Failure, which each exported function returns; they never issue messages.

The literal contract

Registering natural numbers is checked strictly: the type must live in Type with no parameters, indices or universe parameters, and its constructors must be exactly a zero and a successor. An operation is registered for a role, such as "Multiplication" or "LessEqual", and must have the role's type. The kernel then computes it on literals with Wolfram integers and trusts that the operation's definition computes the same, as Lean's kernel trusts GMP for Nat.mul and the rest; a registration is part of the trusted base, as an axiom is.

Interface

(* a term carries the environment its constants come from; without one, it is in the prelude *)
TypeOf[TypeTheoryTerm[2 + 3]]                                    (* TypeTheoryTerm[NonNegativeIntegers, prelude], shown as ℕ *)

  TypeTheoryInductiveType[NaturalList, TypeUniverse[1], {
    EmptyList -> NaturalList,

  }],
  TypeTheoryDefinition[Doubled, Function[{Typed[n, NonNegativeIntegers]}, n + n]],
  TypeTheoryTheorem[TwoPlusTwo, 2 + 2 == 4, EqualityReflexivity[4]]

Elaboration

Elaboration turns what a person writes into a core term. It is not trusted. Every term it produces is checked again by the kernel with no metavariables left, so a mistake here can make elaboration fail but cannot let an ill-typed term through.

  • Implicit arguments. An implicit binder gets a metavariable: a == b stands for Equal[A, a, b], and EqualityReflexivity[4] finds its type argument.
  • Universe levels. A constant gets a level metavariable for each universe parameter. When a metavariable is solved, its type is unified with its solution's type, which is what solves the levels.
  • Unification. First-order unification with a fallback to weak head normal form, and higher-order pattern unification: ?P[x] =?= t, with x a variable, solves ?P = Function[{x}, t], and a variable applied to the pattern's variables solves as that variable.
  • Aliases. A symbol whose value is a declared constant stands for it, as Naturals = NonNegativeIntegers does, unless a binder of the same name is in scope.
  • Expected types first. An argument whose type is still an unknown applied to arguments, such as the proof of P[w] in ExistsIntroduction[2, EqualityReflexivity[4]], waits until the type of the whole application has been unified with the expected type. That is what determines P.
  • Binder types come from the expected type when they are left out: Typed[Function[{x}, x + 1], TypeSpecifier[{NonNegativeIntegers} -> NonNegativeIntegers]].
  • Names overloaded by type. True, False, Not, And and Or stand for the propositions or for the constants of the Booleans, named by strings so that nobody needs to write them: "true", "false", "not", "and" and "or". The expected type decides when it can: a type or Prop takes the proposition, Booleans the Boolean. Otherwise each meaning is tried with the elaboration state restored after, as Lean tries the meanings of ambiguous notation, and the one that fits is taken. A name both meanings fit becomes a metavariable of its expected type and waits until that type is known, at the latest when the binders around it close or the term is finished; a name still undecided then is ambiguous, and Typed must say which it is. Agda resolves overloaded constructors the same way.

Metavariables do not yet carry their own local contexts, as they do in Lean. A solution that names a variable outside its scope is caught by the kernel's final check, not prevented, and shows up as an elaboration failure. Instances and coercions are not implemented.

Rules

The rules of a type theory, what the kernel allows and computes, are a value apart from the declarations an environment assumes. TypeTheoryRules holds them, every environment carries the rules it was started with, and the kernel checks each declaration and term by the rules of its environment. Terms carry their environment, so switching theory means choosing an environment. Elaboration, display and tactics are shared, since they only produce terms that the environment's kernel checks.

  • Prop. "CalculusOfInductiveConstructions", the prelude's rules, has an impredicative universe of propositions with proof irrelevance, K-like reduction and elimination of subsingletons. "MartinLofTypeTheory" has none: every universe level must be at least 1 whatever its parameters are, recursors eliminate into Type u, and a theorem may state any type.
  • Rewrite rules. Where the rules allow them, TypeTheoryRewriteRule[name, ForAll[binders, lhs -> rhs]] makes an axiom compute, as Dedukti's rewriting and Agda's --rewriting do: the left side is the axiom applied to a pattern, the right side has its type, and weak head normalization rewrites a match. A rule is trusted like an axiom. Lean's quotient types, whose computation rule Lean's kernel builds in, are axioms with one such rule; the tutorial Rules and Computation declares them.
  • Homotopy type theory. TypeTheoryEnvironment["HomotopyTypeTheory"] follows Martin-Löf rules with rewrite rules, with paths, univalence as an axiom, and the circle, whose induction computes on its base point by a rewrite rule. Univalence needs the rules, not only the axiom: on the prelude's rules, an equality in Prop eliminates into types and has all its proofs equal, so transport along any path would be the identity, and the same declarations prove False. A test checks exactly that.

Recursors are generated by the rules, so declarations read back by Normal rebuild an environment under its own rules but need not check under others. Moving content between rules is the work of translations, which the target kernel checks again like any other declaration.

Proof assistance

Proof states

A proof state holds a partial proof term with holes. Each hole is a metavariable, an open goal with its own hypotheses and type. A tactic works on the first goal and assigns its metavariable a term, which may contain new metavariables: the new goals. A proof state is immutable data, so undo and branching cost nothing. In a notebook a proof shows each goal as its hypotheses over the turnstile, with the constructor's name on goals that come from induction.

Tactics

"Apply", termApplies a term to as many new goals as its conclusion needs. The goals that others depend on come last, and solving one goal can solve another it mentions.built
"Reflexivity"Solves a == b when the sides are equal by computation.built

A session

proof = TypeTheoryProof[ForAll[{Typed[n, NonNegativeIntegers]}, 0 + n == n]];
proof = TypeTheoryTactic["Introduce", n][proof];        (* n ∶ ℕ ⊢ 0 + n == n *)
proof = TypeTheoryTactic["Induction", n][proof];        (* case NaturalNumberZero ⊢ 0 + 0 == 0, case NaturalNumberSuccessor ⊢ ∀ n, 0 + n == n ⇒ 0 + (n + 1) == n + 1 *)
proof = TypeTheoryTactic["Reflexivity"][proof];         (* 0 + 0 == 0 by computation *)
proof = TypeTheoryTactic["Introduce", k, ih][proof];    (* k ∶ ℕ, ih ∶ 0 + k == k ⊢ 0 + (k + 1) == k + 1 *)
proof = TypeTheoryTactic["Exact", EqualityCongruence[NaturalNumberSuccessor, ih]][proof];

proved = TypeTheoryEnvironment[{TypeTheoryTheorem[ZeroLeftIdentity, proof]}];
TypeTheoryCheck[TypeTheoryTerm[ZeroLeftIdentity[7], proved], TypeTheoryTerm[0 + 7 == 7]]   (* True *)

The last step works because 0 + NaturalNumberSuccessor[k] reduces to NaturalNumberSuccessor[0 + k], so the congruence proof's type matches the goal by computation.

Rule

Simplify, Reduce and their relatives make assumptions a proof may not, about branch cuts or generic parameters. Their output is a suggestion. It enters a proof only as a term the kernel accepts.

What is trusted

Five files and the core declaration functions decide what is a theorem:

  • CoreTerms.wl
  • TypeChecking.wl
  • InductiveTypes.wl
  • NaturalNumbers.wl
  • Environment.wl

Together that is about 1,400 lines with comments and usage messages. Everything else, including the elaborator, the tactics and the display, can make a proof fail but cannot make a false statement pass.

An environment is a handle to a store whose definitions anyone can change by hand, so a store could claim anything. TypeTheoryCheck[environment] replays the declarations in order on an empty environment with the core functions. It regenerates every constructor and recursor from its inductive type, registers the natural numbers again under the strict contract, and compares every record with the one in the environment. The tests forge a theorem's statement, a recursor's elimination universe and the definition of addition, and the replay catches each. Axioms are trusted by definition and stay visible as axioms.

The Lean bridge

Lives in LeanLink

The engine never needs Lean. The bridge is part of LeanLink, which loads TypeTheory on the bridge's first call, so the dependency points from LeanLink to TypeTheory and never the other way.

From Lean

LeanToTypeTheory[env, name] imports a Lean constant with its dependency cone into a TypeTheoryEnvironment, where TypeTheory's kernel checks each declaration again, independently of Lean's.

  • Terms. Lean's expressions, LeanLink's Lean* heads with de Bruijn indices, become exact surface syntax: every application is written with Construct, so nothing is filled in again, every constant is at explicit universe levels with Subscript, and Lean's proj is t[[i]].
  • Names stay held strings: "Nat.zero_add" is the constant "Nat.zero_add", and Nat.rec is InductiveRecursor["Nat"]. Lean's Nat is registered as the natural numbers, so literals mean the same on both sides.
  • Universe parameters are read by type-checking a constant at placeholder levels, so the native shim needed no change.
  • Inductive types are read from the types of their recursors. TypeTheory generates its own constructors and recursor, and each recursor is compared with Lean's.

Eq.symm, congrArg, And.comm, Nat.add_zero, Nat.zero_add and Nat.succ_add import and check. The cone of Nat.zero_add has 43 declarations, Lean's structures and its compiled recursion among them. All 1,381 constants of Lean's Init.Prelude import and check: its syntax trees, nested in arrays, as mutual blocks with auxiliary types; its string literals, written as Lean's kernel reads them, String.ofList of the characters; its arithmetic on large literals, computed with integers once the bridge registers Nat.add, Nat.mul, Nat.ble and the others; and its quotients, with their computation rule as a rewrite rule.

To Lean

TypeTheoryToLean[env, name] writes TypeTheory declarations as Lean source, with every application explicit (@f a b) and every universe level given. The prelude's constants become Lean's Init constants: NonNegativeIntegers is Nat, Equal is Eq, and Plus is Nat.add, which computes the same on constructors. The prelude's axioms are Lean's own, propext, funext and Classical.choice. Everything else is declared in the namespace TypeTheory. LeanImportString compiles the source, so Lean's kernel checks the proof: the proof of 0 + n == n by induction in Proof assistance exports, and Lean accepts it, as it accepts the prelude's proof of the excluded middle with the axioms of its own Classical.em. Lean's kernel follows the calculus of inductive constructions, so an environment of other rules, without Prop or with rewrite rules, is refused rather than written as source Lean would reject.

What must always hold

  • Agreement. On every imported declaration the two kernels give the same verdict, and every recursor TypeTheory generates agrees with Lean's.
  • Round trip. Lean to TypeTheory to Lean returns the same declaration. The export leaves imported constants to Lean today, so this is checked as the export learns to write them.

Still to build

  • Proof terms share subterms heavily and WXF does not. A table of distinct subterms, sent once each, will lift the depth limit that LeanLink's export has on large proofs.
  • Declarations back through Lean's Environment.addDecl in process, besides source.
  • Quotients in the kernel rather than as rewrite rules.

A compiled kernel

The symbolic kernel is right for a prototype and for interactive work: it is short, readable, and easy to test. For thousands of declarations, the hot paths of substitution, reduction and comparison need to run compiled. The plan is a second representation for the kernel only, with no native library and no change above it:

  1. Arrays for terms. Each core term becomes a node in a hash-consed table of packed integer arrays: an opcode, child indices and a payload. Equal subterms share one index, which also gives the shared-subterm encoding the bridge needs.
  2. Compiled structure. Substitution, lifting, abstraction and the loose-variable range of each node, written with FunctionCompile over the arrays.
  3. Compiled reduction. β, ζ, δ and ι, with the environment's definitions and recursor rules as tables of node indices.
  4. Compiled comparison. Definitional equality with a cache of pairs already shown equal, keyed by node index, and lazy unfolding by definitional height.

Elaboration, tactics and display stay symbolic. The symbolic kernel stays as the reference, and each compiled function is tested against it on the same inputs.

Risks and open questions

RiskMitigation
Speed on large proof termsThe compiled kernel, structural caches, and Lean's kernel for bulk checking through the bridge.
Nested and reflexive inductive types, where independent checkers most often go wrongAfter mutual families, with Lean's own recursors to compare against.
Built-in symbols evaluatingEvery entry point holds its arguments, and terms become inert syntax trees before anything looks at them. TypeOf also holds its argument, so a symbol holding a term needs TypeOf[Evaluate[t]], or TypeTheoryCheck[t].
Built-in names with another meaning, such as SortUniverses have their own head, TypeUniverse; only symbols whose meaning matches become constants.
Prop confused with BooleansPropositions are types in Prop and never booleans; a decision procedure will be the only bridge between them.
Escaping variables in elaborationCaught by the kernel today; metavariable contexts will prevent them.
A proof state holds its environmentIts display is not interpretable and the environment's summary box stores no copy, so notebooks stay small.

Open questions

  • Lean's names became held strings. Should imported constants that the prelude has, such as Nat and Eq, become the prelude's built-in symbols on import, as they do on export?
  • Should the prelude grow toward Lean's Init by import through the bridge, or stay a small hand-written library with the bridge relating the two?
